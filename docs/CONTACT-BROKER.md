# 牵线（联系方式中介）

甲在结果里看中乙，想认识。平台在中间转一次：乙看到甲的极简信息，自己决定同意与否；乙同意后，平台把**甲**的联系方式发给乙一次，之后双方自己联系。乙的联系方式从不经过平台发给甲。

## 1. 已确认的规则

| # | 规则 | 实现 |
|---|---|---|
| 1 | 乙拒绝，平台只告诉甲“对方暂未同意”，不暴露乙的任何细节 | 拒绝、过期、乙关闭牵线、乙退出人选池，甲看到的都是同一句“对方暂未同意”，甲分辨不出原因 |
| 2 | “愿意被牵线”只是允许别人发来请求，每一次请求都要乙主动点“同意”并再确认一次 | 同意接口必须带 `confirm: true`；页面上点“同意”后还会弹出确认框；没有自动同意 |
| 3 | 乙同意前甲可以取消；乙同意后不可撤回，但甲可以屏蔽乙 | 只有“等待回应”的请求能取消；同意后联系方式已发出，只能屏蔽 |
| 4 | 乙只看到甲的极简信息：性别、年龄段、城市、职业大类、匹配契合点 | 年龄按 5 岁分段；契合点只给条数（“他符合你 4/6 条，你符合他 3/5 条”）；不含精确年龄、收入、资产、照片、昵称、身高、学历 |
| 5 | 结果页上，没开放牵线的人显示“该用户暂未开放牵线” | 不解释原因：没打开开关、退出人选池、屏蔽了你，看起来都一样 |
| 6 | 联系方式按 L3 加密，不进人选池、不参与评分，用后隐藏，随时可删 | 单独加密存放在 `data/contacts/`；乙记下号码后点“我已记下”，号码立即从服务器上删掉 |

## 2. 边界情况

| 场景 | 处理 |
|---|---|
| 甲取消后重新发起 | 允许，冷却 1 小时，防止误触后马上重发 |
| 乙没同意（拒绝 / 7 天未回应 / 乙关闭牵线 / 乙退出人选池）后甲再发 | 允许，冷却 7 天 |
| 屏蔽 | 单向：甲屏蔽乙，乙不能再向甲发起，乙看到甲是“暂未开放牵线”；乙屏蔽甲同理。屏蔽不通知对方，也不影响对方被其他人联系 |
| 联系方式已发给乙后，甲删除联系方式 | 已发出的不可撤回：乙还没点“我已记下”时，仍能看到那一次的号码；甲之后不能再发起新请求 |
| 甲删除联系方式 | 甲还在等待回应的请求自动撤回 |
| 乙关闭“愿意被牵线” | 乙收到的、还在等待的请求自动作废，甲看到“对方暂未同意” |
| 乙关闭“让别人也能找到我” | “愿意被牵线”自动关闭，且在重新打开人选池之前不能打开 |
| 打开“愿意被牵线”时还没留联系方式 | 自动用登录手机号；可以在“牵线”页改成微信号 |
| 冷却中 | 卡片上写明大约还要等多久 |
| 双方互相想联系 | 各自独立发起，互不影响 |
| 任何一方有“必须有”没达到 | 不出现“想联系”按钮，服务端也拒绝 |
| 演示模式（模拟人选） | 模拟人选不能牵线，页面上说明 |
| 删除账户 | 联系方式、所有相关请求（包括对方还没记下的那份号码）、双方的屏蔽记录一起删除。对方已经抄走的号码平台无法收回 |

## 3. 流程与状态

```
甲：点“想联系他/她” → 留联系方式（首次）→ 看清楚会发什么 → 勾选同意 → 发送
                                   │
                                   ▼
                           [等待回应]（7 天）
          甲取消 ┌───────────────┼───────────────┐ 乙点同意并再确认
                 ▼               ▼               ▼
            [已取消]       [对方暂未同意]     [已同意]
            冷却 1 小时      冷却 7 天        甲的联系方式发给乙一次
                                             乙点“我已记下”后从服务器删除
```

| 内部状态 | 甲看到 | 乙看到 |
|---|---|---|
| `pending` | 等待对方回应（可取消） | 收到一个请求（同意 / 暂不同意 / 屏蔽） |
| `accepted` | 对方已同意，联系方式已发给对方（可屏蔽） | 对方的联系方式（我已记下 / 屏蔽） |
| `declined` `expired` `withdrawn` | 对方暂未同意 | 不再显示 |
| `cancelled` | 已取消 | 不再显示 |

## 4. 接口

所有接口都要登录令牌，只能操作和自己有关的请求。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/me/broker` | 自己的联系方式、开关、收到的和发出的请求 |
| PUT | `/api/me/broker/contact` | 留下或修改联系方式 `{ type: 'phone'\|'wechat', value }` |
| DELETE | `/api/me/broker/contact` | 删除联系方式 |
| PUT | `/api/me/broker/willing` | 打开或关闭“愿意被牵线” `{ willing }` |
| POST | `/api/me/broker/requests` | 甲发起 `{ alias, consent: true }`，`alias` 是结果里的代号 |
| POST | `/api/me/broker/requests/<id>/cancel` | 甲取消（仅等待中） |
| POST | `/api/me/broker/requests/<id>/accept` | 乙同意 `{ confirm: true }`，返回甲的联系方式 |
| POST | `/api/me/broker/requests/<id>/decline` | 乙暂不同意 |
| POST | `/api/me/broker/requests/<id>/seen` | 乙记下号码，服务器删除这份号码 |
| POST | `/api/me/broker/requests/<id>/block` | 屏蔽这个请求里的对方（甲乙都可以） |

结果接口里，每位人选卡片多一个 `broker.state`：`open` 可以联系、`closed` 暂未开放牵线、`ineligible` 必须有没对上、`pending` 已发出、`accepted` 已牵线、`cooldown` 冷却中、`demo` 模拟人选。卡片仍然只带代号，不带内部 id；发起时服务端在你自己的人选池里用代号找回对方。

## 5. 存储与隐私

- `data/contacts/<id>.json`：联系方式，AES-256-GCM 加密。只在乙同意那一刻读取一次。
- `data/broker.json`：请求、开关、屏蔽，整体加密。请求里的极简信息在发起时生成；同意时复制一份加密的号码给乙，乙点“我已记下”后删除。
- 联系方式不进入人选池、评分、结果、统计和导出给别人的任何数据；本人导出时包含自己的联系方式和开关。
- 审计日志只记动作和请求 id，主体是带密钥的哈希，不记号码。
- 冷却时间、过期天数在 `config/app.json` 的 `broker` 里配置。

## 6. 以后再做

- 通知：现在乙要打开“牵线”页才看到请求（首页和结果页有提示）；以后接短信或微信模板消息。
- 手机号验证：现在只校验格式，正式上线前加短信验证码，防止留别人的号码。
- 限流：同一个人一天能发起的请求数。
